## 0. 执行摘要

Etera_Game 的**首要产品目标是方向 B**：构建一个通用的、现代化的 ERA / Emuera 风格叙事游戏引擎，而不是仅仅制作一款角色养成游戏。采用 Python + Lua + Vue/WebSocket 的前后端分离方案，主要目的是突破传统终端/窗口呈现、资源加载与自定义交互的限制，保留脚本驱动叙事和 Mod 创作能力。

当前以**灵梦线**作为首个完整参考实现，通过真实角色剧情驱动并验证时间、地图移动、商店、人物关系、事件和交互模块等基础能力；灵梦线中的需求已反向推动这些系统实现。现阶段基础功能总体可用（根据开发者反馈），AI 利用项目实例和 `DSL.txt` 已可以较好地产生 Lua 内容。近期更值得投入的是**运行时/前端 UI 切换稳定性**，而非盲目扩充 DSL 指令。

已经观察到的突出问题：切换界面时偶发进入一个**由引擎自身绘制的默认空界面**——仍有背景、布局与主题色，但没有文字、按钮与游戏内容。此现象目前不等于浏览器白屏，也**不能直接断定**是 Lua 调度器的问题。优先检查 UI 模式栈、界面内容状态、组件生命周期、WebSocket 事件时序及旧请求覆盖。

当前倾向的长期解法：以**常驻主游戏界面 + 独立前端交互模块/浮窗宿主**替代频繁进行全页面模式切换；每个模块通过输入数据、结果返回与可选持续消息与 Lua 通信。**浮窗化是架构优化，不可代替查明空界面根因。**

## 1. 信息来源与事实边界

### 1.1 已明确的开发者决策与反馈

- 首要目标是通用 ERA / Emuera 风格引擎；角色路线只是引擎能力验证，而非产品最终边界。
- 重做动机主要是传统环境表现力与资源加载限制；Web 前端更适合现代画面和扩展。
- 灵梦线是当前主线验证；时间、商店、地图移动等功能源于这条线的实际需求。
- 第三方玩法 UI 应尽量是**独立前端模块**，通过数据与引擎交互；核心引擎不内置所有游戏。
- 独立模块可接收初始化数据，完成交互后返回游玩结果或必要数据；复杂模块未来可允许持续消息。
- 目标是纯本地使用，采用本地自选 Mod 的信任模式；安全边界要实用，但不应在当前阶段过度设计。
- 长期计划制作可视化编辑器，用于基础编辑与预览；提供 AI 专属预设、项目样例和 DSL 说明，降低无代码作者的创作门槛。
- 现阶段以 AI 生成为主开发 Lua 剧情，实际使用效果总体良好；尚需完善部分引擎调度或 UI 状态问题。
- 当前异常是**正常绘制的默认空壳 UI**，不是空白浏览器页面；拟减少页面切换，使用浮窗打开新 UI。

### 1.2 仓库公开 README 确认的背景（2026-11-02 查阅）

- Python 3.12 + asyncio 后端，Lua 沙箱、事件总线、状态管理。
- Vue 3 + Vite + TypeScript 前端；WebSocket JSON 通信。
- `DSL.txt` 为公开 Lua Mod 契约，README 记载 53 个指令（需以实际文件内容为准）。
- README 记录 Phase 3 引入 UI 模式栈；Phase 4 引入设置、音频、Canvas 小游戏原型。
- 文档事实来源包括 `CONTEXT.md`、`docs/architecture.md`、`docs/requirements.md`、`docs/progress.md` 与 `docs/adr/`。

## 2. 产品定位与设计原则

### 2.1 三层产品方向

| 层级 | 任务 | 现阶段优先级 |
|---|---|---|
| **Etera Runtime** | Lua 脚本、状态/事件、前后端通信、资源加载、交互模块宿主 | **最高** |
| **Etera Editor** | 剧情/角色/地图的基础编辑、事件调试、即时预览 | 后续 |
| **Etera AI Toolkit** | 为 AI 提供 DSL、项目样例、模板、契约验证及报错反馈 | 现阶段持续积累，后续产品化 |

原则：三者以**稳定的数据格式和接口契约**衔接；编辑器和 AI 工具不应迫使 Runtime 依赖特定模型或编辑器。

### 2.2 灵梦线的职责

灵梦线是**Reference Implementation**，而不仅是内容 Demo。验收不仅关注“能玩”，还要关注：

1. 剧情作者能否仅修改 Lua 和资源/配置实现完整角色线。
2. 时间、移动、商店、关系与事件机制是否由游戏规则驱动，而非锁死在引擎中。
3. 多阶段剧情能否安全地等待交互、恢复、保存与退出。
4. 相关功能能否在**一个非东方设定的最小测试 Mod**中复用。
5. AI 是否能凭 `DSL.txt` + 项目实例输出合规脚本，且出错时能得到可行动的诊断。

### 2.3 运行时与游戏规则的边界

- Runtime 负责状态保存、事件派发、模块生命周期、渲染宿主、消息投递、异常隔离。
- 游戏/Mod 负责世界观、一天的时段划分、地图连接、商店价格、角色关系成长、剧情分支等业务规则。
- API 扩展的判断标准：优先判断是 DSL **表达力不足**，还是现有指令的**执行稳定性不足**；后者先修调度。

## 3. 独立 UI 模块扩展方案

### 3.1 推荐方向

采用**独立前端交互模块**：Lua 发起调用，Runtime/前端宿主按模块 ID 加载独立 UI，传入结构化数据；模块在完成后返回结构化结果；如未来需要复杂管理面板，可通过消息通道做多轮交互。

基础时序：

```text
Lua/Scenario -- start(moduleId, input, requestId) --> Runtime/WS --> UI Host
       |                                                  |
       |<---------- result(status, data, requestId) -------|
       v
验证结果、更新游戏状态、继续剧情
```

这里的 `start`、`result` 等均是概念名，不应在尚未核对源码时擅自改动实际 DSL/WS 协议。

### 3.2 两种交互模式

| 模式 | 说明 | 典型场景 |
|---|---|---|
| 一次性请求-结果 | 初始化 → 交互 → 结果 → 销毁 | 小游戏、解谜、抽奖、特殊演出 |
| 持续消息交互 | 初始化 → 多轮动作/状态消息 → 结果/关闭 | 装备、角色管理、复杂战斗、经营面板 |

优先**复用既有小游戏机制**，先通过第二种截然不同类型的 UI（如商店/角色面板）验证抽象，再冻结通用接口。不要为了假想需求过早制造大型 SDK。

### 3.3 最小模块契约建议（未来方案）

- 身份：`moduleId`（建议 `modId:moduleName` 命名空间）。
- 请求：`requestId` / 交互实例 ID、初始化参数、可选上下文。
- 结果：`status = completed | cancelled | failed`，以及结果载荷与错误说明。
- 生命周期：同一个请求只能完成一次；关闭和异常必须能够解除 Lua 等待；陈旧请求不得关闭更新的界面。
- 数据：仅允许跨边界传递可序列化结构；明确大小限制与版本。
- 状态所有权：持久游戏状态以 Lua/Runtime 为准；前端是交互呈现和临时状态，不直接随意改存档。
- 兼容性：注明协议版本，未知模块或协议不符时返回显式错误，而不是落入默认空 UI。

### 3.4 本地信任模型

纯本地确实减少远程部署的攻击面，当前无需为此中止主要开发。但第三方 JS 一旦在相同页面上下文执行，仍可能读取应用状态或干预接口。建议采用分级信任：自带可信模块直接加载；面向外部分发的模块以后再考虑 iframe 隔离、权限声明与消息校验。不要将“本地”理解为“任何第三方代码天然安全”。

## 4. AI 内容生产及后续工具规划

### 4.1 当前已被开发实践验证的工作流

```text
项目参考实例 + DSL.txt + 需求描述
        ↓
       AI 生成 Lua / 配置
        ↓
    在 Runtime 中运行测试
        ↓
反馈不合规 API、事件/状态问题
        ↓
修订脚本、模板、DSL 文档或 Runtime
```

保留 AI 生成的成功实例与失败修复案例，可逐步形成可验证的创作规范。

### 4.2 可视化工具分阶段

- **第一期：预览/调试工具**——直接运行某段事件、查看状态和触发条件、错误定位、资源预览。
- **第二期：基础编辑器**——角色、地图、商店、事件配置的表单化编辑。
- **第三期：AI 辅助工作台**——将自然语言需求转化为合规文件，静态检查并预览结果。

AI 不应仅拥有提示词；应有**可机器验证的 API 参数、返回值、资源标识和运行约束**。目标是降低代码门槛，但避免承诺任意复杂自定义交互必定零代码且一次成功。美术/CG 另设创作流程。

# 5. UI 默认空界面 Bug 专项研究

## 5.1 问题定义

**现象（来自开发者直接观察）：** 进行 UI 页面切换时，偶发跳转到由引擎自行渲染的“纯默认”界面：主题色、背景和基础框架存在，但是没有页面功能、文字、按钮或剧情内容。

**触发：** 目前与页面/模式切换有关，尚未提供最小复现路径；不确定是否与退出小游戏、商店、存读档或其他特定模式相关。

**影响：** 游戏无法继续正常交互（具体是否可以恢复待确认），阻断角色线的完整验证，也将影响未来插件宿主可靠性。

**确认程度：** 已知表现，**未知根因**。不能因为是“默认界面”就断言发生了模式栈 pop 过多；也不能因为异步架构存在就判定是 Lua Future 调度错误。

## 5.2 候选原因与验证证据

| 优先排查 | 假设 | 查证方法 | 若证实的最小修复 |
|---|---|---|---|
| P0 | 模式栈 pop/reset/replace 导致栈顶回到默认壳 | UI 模式改变日志记录操作、调用源、前后栈 | 合法状态转移校验；禁止多次 pop；确定退出后的基础模式 |
| P0 | 模式切换成功，但内容数据（文字/按钮/scene）未到达或被清空 | 同时记录 `mode`、内容数量、WS 消息顺序 | 模式和必要数据原子提交；在未准备就绪前保留旧界面或显示加载态 |
| P0 | 旧 WebSocket 消息/旧操作异步回调覆盖新界面 | 附上 `requestId`、交互实例 ID、递增序号/时间戳；复现乱序 | 根据实例 ID / epoch 丢弃过期界面更新 |
| P1 | 退出模块发生两次、关闭回调误关当前新模块 | 对每个 open/close/cancel 记录唯一实例 | 幂等关闭；只能关闭创建者对应的 UI 实例 |
| P1 | Vue 组件卸载重挂、watch 清理重置了共享显示状态 | 记录组件 mount/unmount 及 store 变化 | 持久数据脱离临时组件生命周期；必要时将主界面常驻 |
| P1 | Lua 事件异常、中断或未恢复，使前端停在等待填充的壳 | 对照脚本生命周期、Future 结果、WS requestId | 错误/取消时返回可见的恢复 UI，清理 pending 任务 |

上表为假设与调查顺序，不是概率结论。只有得到**日志或可复现测试**后才能定位根因。

## 5.3 首先实施：建立可追踪的 UI 状态转移

建议统一所有 UI 状态变更入口，并输出结构化日志（尽量不要在每个组件里手工打印）。字段示意：

```json
{
  "event": "ui.transition",
  "action": "push|pop|replace|reset|content_update",
  "source": "lua|ws|user|component|system",
  "fromMode": "game",
  "toMode": "shop",
  "stackBefore": ["game"],
  "stackAfter": ["game", "shop"],
  "requestId": "request-123",
  "interactionId": "interaction-456",
  "sessionId": "session-1",
  "contentSummary": { "texts": 2, "choices": 4 },
  "reason": "open-shop"
}
```

以上字段名仅作设计示例。日志至少应该可以回答：

1. 哪一条动作**首次**让模式变成默认值？
2. 切换到默认模式**之前**是否存在内容？内容在哪一步丢失？
3. UI 模式变化是玩家动作引起，还是 Lua / WebSocket 后续消息引起？
4. `requestId` 或模块实例是否对应当前活跃交互？
5. 组件卸载是否发生在异常前后？

> 技术提醒：单纯给 `watch(currentPage)` 打印 `new Error().stack`，堆栈通常只指向 watcher 执行处，未必能回溯原始写入点。应当在**统一的状态写入入口**（例如实际存在的 navigate、push、pop 等方法）捕获调用来源。

异常发生时应保留最近约 100–300 条状态转移/WS 事件的循环缓冲区，必要时导出 JSON；避免日志本身造成刷屏和性能损耗。

## 5.4 推荐的根因排查顺序

### Step 1 — 找到默认壳的真实来源

在实际 Vue 源码中定位空界面组件/模板、默认 mode/scene、空内容渲染条件。搜索其被引用路径和所有 mode 写入口。特别确认 README 所记载的 UI 模式栈在当前 v2 代码中的**实际形态**，不可将旧版 v1 的模式栈实现直接当作当前代码。

### Step 2 — 构建状态与事件时间线

采集以下链路：用户点击 → Lua 请求 → WS 消息 → UI 栈操作 → 内容更新 → 模块关闭/返回。让 UI 模式变化与内容变化能在同一时间线上对齐，而不是分别记录零散日志。

### Step 3 — 最小复现

从稳定入口反复执行“打开/关闭商店或系统界面 30–100 次”“连续快速切换”“重复点击关闭”“异常返回”“延迟/乱序到达的 WS 结果”“切换时存读档/退出”等场景。首先建立**可稳定复现的单个场景**，再修复。

### Step 4 — 优先打最小补丁

根据证据选择单点修复，如：禁止弹空栈、拒绝失效 request、对关闭操作去重、内容准备后再激活模式、异常恢复到上一合法状态。

### Step 5 — 回归与复盘

复现脚本和测试保留下来，纳入前端 E2E 或 store/状态机测试。记录“触发条件、根因、修复位置、回归用例”到 `docs/progress.md` 或相应 bug 记录。

## 5.5 浮窗方案：后续架构优化，而非先验修复

建议 UI 分为两个独立状态域：

```text
Application Shell（主题、背景、公共容器，常驻）
  ├─ Base View（主菜单 / 游戏主界面 / 读档等必要上下文）
  └─ Overlay Host（地图 / 商店 / 背包 / 小游戏 / 第三方模块）
       └─ Interaction Instance（唯一 ID、输入、结果、关闭状态）
```

- 日常临时交互优先浮窗，不卸载游戏主界面。
- 应用级上下文切换（新游戏、返回标题、读档等）仍需要可靠、显式的页面切换。
- Overlay 的开启/关闭不应直接修改基础页面 mode。
- 允许“关闭当前交互”但不允许旧模块随意清空整个模式栈。
- 若模块打开后没有收到所需数据，应显示明确加载/错误状态，而不是裸露出无功能的空壳。

**建议渐进迁移**：先选择一个目前易于复现问题的系统界面转换为 Overlay，保持 DSL 不变，通过 UI 宿主适配消息，再用日志和测试比较异常率；验证有效后迁移其他模块。

## 5.6 状态机/协议最低限度约束

1. `interactionId` 唯一、一次调用只允许一次 `resolve`。
2. 对 `complete/cancel/error` 统一终态处理；终态不得再次关闭或恢复其他实例。
3. 请求 ID/会话代际必须与当前 active 实例匹配；过期响应不得改写 UI。
4. 在当前模式还未构建内容之前，不应显示成“成功进入但无操作”的空壳；可以保留旧 UI、显示 loading 或可恢复错误面板。
5. 用户退出/脚本异常时，前端与 Lua 等待双方都要得到终止信号（若现有 DSL 不支持，优先在内部适配，避免直接破坏公开 API）。
6. UI 恢复时明确恢复的是**模式**还是**内容快照**；不能只恢复 mode ID 却丢失文本/选项。

## 5.7 必备回归测试清单

- [ ] 正常：从叙事界面进入商店，返回后原剧情/行动选项可用。
- [ ] 正常：连续打开不同交互模块，关闭时只恢复对应宿主。
- [ ] 压栈/出栈：额外 pop、重复 cancel 不会落入空默认模式。
- [ ] 乱序：旧 `requestId` 返回时不得覆盖当前界面。
- [ ] 断线：等待中的交互获得明确错误或可恢复态。
- [ ] 异常：模块抛错后不丢失主界面且能够继续交互。
- [ ] 快速操作：重复点击打开/关闭不会产生双重回调。
- [ ] 内容原子性：页面切换前后的内容状态有定义，不能出现永久空壳。
- [ ] 存读档：读档重建 UI 时不存在孤立的旧交互实例。
- [ ] 灵梦线端到端：至少一次包含地图、商城、对话、小游戏/特殊 UI 的连续游玩流程。

### Bug 修复完成标准

- 有可复现步骤或足以证明根因的状态事件记录。
- 根因经代码路径和测试证实，不仅是“改成浮窗后较少发生”。
- 测试覆盖异常场景，正常切换 100 次（次数可依自动化执行成本调整）无空壳。
- 不破坏现有 `DSL.txt` 公共语义和存档结果。
- 发生未知状态时存在可见错误与返回路径，不再静默进入无功能界面。

## 10. 修复进展（2026-11-03）

按本文 §5 的排查顺序，已定位并修复以下可进入空壳的路径：

| 路径 | 根因 | 修复 |
|---|---|---|
| 额外 pop / 重复退出小游戏 | `popMode()` 空栈时回退到 `game` | 空栈 no-op；`finishMinigame` 幂等；P3 把小游戏迁到 Overlay Host、删除模式栈 |
| 睡觉结果迟到 | 玩家回主菜单后 `sleep.result` 仍切到 game 并清空画面 | 只在 `hub` 处理；其余视为过期消息 |
| 读档结果迟到 | 读档异步返回时界面已切走 | `pendingLoadEpoch`/`uiEpoch` 代际校验，过期丢弃 |
| 事件结束迟到 | abort 后脚本 `finally` 仍发 `event.done`，把主菜单顶成 Hub；旧事件 done 会结束新事件 | 只在 `game` 处理；`pendingEvent`（事件名 + 代际）匹配才接受 |
| 小游戏启动迟到 | `minigame.start` 在主菜单到达 | 只在 `game` 且无活动覆盖层时处理 |
| Hub 行动被拒 | 前端已切 game 并清空内容，失败只弹 toast | 无内容时回收 `enterHub()` |
| 读档面板未关闭 | `load.result` 成功后 `panel='load'` 残留 | 成功后清 `panel`/`detailChar` |
| 未知模式空白页 | `App.vue` 落到无匹配分支的 GameScreen | 渲染「界面状态异常」恢复页 |
| 自检从 Hub 触发 | 剧本先弹选项，但 Hub 不渲染 ChoiceMenu | `runSelftest()` 先切叙事界面 |
